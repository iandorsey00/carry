# Education Specification Architecture Assessment

Status: proposal for review.

## Recommendation

Keep Carry as the learner-facing application and first reference implementation. Keep its curriculum, routes, and specialized practice engines in place. Develop the proposed education specification as an independently versioned draft inside the Carry repository, alongside a small collection of example packages and conformance fixtures.

When the model has been tested against recall, multimedia, and guided math, ask whether a second consumer can validate or display a course without importing Carry. An independent reader, publisher, or a real memtrain integration can demonstrate that boundary. Extract the specification, schemas, fixtures, and toolkit into one upstream repository when independent use or ownership justifies separate releases. Give the public specification a neutral name at that point. Keep "Carry Education Specification" as a working title for the draft. Keep the toolkit with the specification while their changes and tests are closely coupled.

The gap worth testing is whether one human-readable, offline package can compose explanations, reusable assessments, and guided interactions while keeping its educational meaning outside the application. The course format describes learning material. Carry determines how learning feels, from keyboard focus and mobile entry controls to optional hints and more demanding practice.

## Current Systems

- **Carry Lesson Specification.** CLS v1 declares paragraphs and explicit math runs, figures, response slots, authored problems, hints, transformations, and capability metadata. Its compiler checks engine and catalog compatibility and emits Carry workspace data. The shipped matrix multiplication lesson and the long addition and separable equation examples give the draft concrete cases to work from. Lesson Studio validates and runs temporary CLS lessons in memory. Preserve that authoring path and its saved drafts. [CLS authoring guide](../authoring/README.md) · [Lesson compiler](../core/lesson-spec.js)
- **Carry curriculum and learner records.** Built-in workspaces, course sequences, and the router are existing integration points. Carry's evidence model records correct and incorrect attempts, hint use, and capability counts. Attempt history is bounded and currently keyed by workspace, problem, and step. A portable export needs its own format and explicit revision mapping. [Workspace registry](../core/workspace-registry.js) · [Router](../core/router.js) · [Learning record](../core/learning-record.js) · [Course sources](../courses/)
- **memtrain.** The CSV format supports cues with up to three response slots, synonyms, hints, tags, MTag groups, and per-slot IDs. Missing IDs are derived from cue and response text. The Python engine supports fixed and adaptive sessions across three response stages. Its SQLite store keeps per-item summaries, stage, counts, and due dates keyed by study set and item ID. Those summaries can be migrated as snapshots. They cannot reconstruct a complete attempt history. [memtrain study-set format](https://github.com/iandorsey00/memtrain/blob/main/docs/study-set-format.md) · [memtrain repository](https://github.com/iandorsey00/memtrain)

## Minimum Specification

1. **Course and lesson manifests.** Declare a format version, content revision, stable IDs, title, language, license, and an ordered list of lessons and cards. Each card has an ID and an ordered list of content blocks or references. One card at a time is Carry's default presentation. Readers can provide a continuous view of the same material.
2. **Readable content and assets.** Support Markdown, images with alternative text, and local links to PDF, audio, and video. Provide transcripts or captions where appropriate and a readable explanation for interactive material. For math, test a small, documented TeX-like convention against Carry's MathML renderer and an independent renderer. The baseline meaning must remain available from the files. Keep presentation presets in the reader.
3. **A reusable question bank.** Start with single choice, multiple selection and exact text with explicit accepted forms. Define stable item, part and option IDs, declared normalization, correct responses, hints, feedback and optional objective and explanation links. Use authored variants initially. Treat difficulty, response demand, and review priority as independent. Specify separately whether a session shuffles options, selects distractors, draws items, or picks a variant. Record the resolved item, variant and option IDs when that matters to interpreting an attempt.
4. **Objectives and assessment references.** Allow questions and cards to reference a locally declared objective by ID. Begin with knowledge checks and practice. Add checkpoint and final assessment policies when a reference course needs them. Completion, demonstrated performance and scheduling remain distinct. Build prerequisites from links first so learners can move freely or return to an explanation.
5. **Versioned widget references.** Supply a namespaced type and version, config reference, objective links, and static fallback. Publish input and evidence semantics for each supported type and document its keyboard, mobile, and assistive-technology behavior. Carry resolves the declaration to a reviewed renderer. A basic reader renders the fallback when it lacks the widget. Keep configuration data separate from executable code.
6. **Validation and portability.** Validate shape, IDs, references, asset paths, compatible versions, accessible fallbacks and bank consistency offline. Add valid and invalid fixtures and document observable behavior for a basic reader and a reader supporting the question profile. Detect ambiguous or overlapping choices where deterministic checks suffice. Review mathematical correctness and distractor plausibility as editorial QA.

Use relative, package-contained paths and human-readable source files. A directory is sufficient for the pilot. Test packaging only after a directory can be opened and checked independently. Distinguish specification version, content revision, item revision and player version. Changes to the meaning or correctness of an item require a new item revision so past evidence keeps its interpretation.

## Integration Boundaries

The specification defines portable meaning. The toolkit validates and converts that data and emits explicit reports for unsupported or lossy conversions. Carry adapts validated packages to its course and workspace interfaces. Toolkit validation must work independently of the DOM, the Carry app and its storage. Carry can supply its registry when checking Carry-specific widget configuration.

Keep CLS v1 as the format for Carry-specific guided math activities. During the pilot, a course references a CLS lesson as a widget payload. Carry passes the original payload to its existing compiler and renderer. A generic reader can show a worked example as fallback. That preserves matrix cells, digit grids and derivation slots without asking a learner to type structural notation. Promote common CLS semantics into the shared specification only once another implementation needs and can implement them.

Start memtrain integration with a converter for one real CSV set. Preserve explicit IDs and persist the legacy IDs alongside generated canonical IDs. Map multi-slot cues without flattening distinct blanks, and keep synonyms separate from distractors. Treat MTag as a candidate-pool hint and exclude every accepted answer from the resulting distractors. Compare fixed recognition, hinted recall, and free response before migrating adaptive scheduling. Trial a separate, read-only SQLite transfer with a report of matched, ambiguous and unmatched items. Carry can preserve existing due dates and stage snapshots where IDs resolve. Keep memtrain available until its CLI and desktop workflows have suitable replacements for their actual users.

Keep progress out of course packages. Design an explicit local export once both pilots can produce comparable evidence. Record content and item revision, attempt outcome, timestamp, and hint or response mode when relevant. Retain raw responses only for an explicit learner-facing purpose. On import, preserve unknown references for later reconciliation and prevent duplicate evidence on repeat import. Use a separate scheduler state snapshot if needed. Carry keeps its existing browser backup path.

## Principal Risks

- **Application requirements become format requirements.** Check the draft with a second reader, ordinary Markdown tools and a real memtrain set. A published schema alone does not prove interoperability.
- **A full authoring system precedes usable content.** Test actual authoring edits and error recovery with one nearby example and a validator. This is especially important for AI-generated lesson data. Freeze syntax only after seeing the same need in multiple pilots.
- **Assessments lose meaning in conversion.** Exercise round trips with fixed fixtures and compare behavior as well as fields. Report unsupported scoring, revision mismatches, and partial widget exports explicitly.
- **Offline does not guarantee exam secrecy.** Keep answer banks separate from learner-facing static exports. Self-checking browser packages necessarily make their scoring data inspectable. Reserve confidential exam delivery for a different trust model.
- **Imported packages introduce executable or external dependencies.** Reject authored scripts and untrusted markup and validate paths, references and resource limits. Test these checks before accepting archive uploads. Content licensing is separate from the reader's source-code license.

## Phased Plan

| Phase | Deliverable and decision |
| --- | --- |
| 1. Draft an experimental profile | Define the minimal manifest, card and item semantics. Settle syntax through examples. Use normative language only for testable requirements. |
| 2. Author three small reference courses | Convert a memtrain vocabulary set, author a short astronomy lesson with a local figure and captioned clip or transcript, and wrap the existing matrix multiplication or separable equations lesson. Open the sources without Carry and see what a learner can still understand. |
| 3. Validate and test interchange | Build a portable validator and reference fixtures. Test one QTI item exchange with a concrete reader and report loss. Check stable references, fallback display and keyboard/mobile behavior. Reassess the repository boundary with evidence from these tests. |
| 4. Pilot in Carry | Open packages through Lesson Studio as temporary local courses with card navigation and an existing guided workspace. Preserve current routes, backups, and course behavior. Compare the learner experience with the existing lesson before migrating any built-in content. |
| 5. Prove recall and portability | Add the memtrain adapter and test staged recall parity. Introduce separate progress export and import after an identity-mapping and restore rehearsal. Publish a stable specification only after a reader without Carry can validate the examples and demonstrate the baseline behavior. |

The first learner-facing test is a short course that can explain a concept, ask a reusable question, and open an existing guided activity. It should be useful to someone refreshing a topic after years away and readable from its source files years after authoring.
